# إصدار الوثائق وتسليمها — المتطلب التاسع

## الفحص والقرار التنفيذي

المشروع Laravel 12.65.0 وPHP 8.2.12؛ قاعدة التشغيل MySQL عبر MariaDB 10.4.32. أُعيد استخدام `CitizenDocument` وجدول الوثائق الموجود، وخدمات جاهزية الاعتماد والأهلية، وجداول الطلبات والخدمات والتقييمات والمرفقات والمواعيد والفحوص والسداد، وآلية صلاحيات الموظف حسب الخدمة. كانت صفحتا الإصدار والتسليم تعرضان مكوّن التجربة المحلية فقط؛ استُبدلتا بواجهات ترتبط بالقاعدة فعلًا.

لا يوجد قالب حكومي أو ترقيم رسمي أو مدة صلاحية قانونية موثقة داخل المشروع. لذلك الأرقام المولدة **داخلية تبدأ دائمًا بـ INT**، والنسخ الإلكترونية **HTML عربية قابلة للطباعة وتحمل تنبيهًا داخليًا أكاديميًا**؛ ليست بطاقات أو جوازات أو رخصًا صالحة قانونيًا. لم تُثبّت مكتبة PDF، لأن Blade الموجود يولد النسخة الإلكترونية المطلوبة دون اعتماد جديد؛ هذه النسخة ليست PDF. القوالب منفصلة لكل نوع وثيقة وقابلة للاستبدال بقوالب معتمدة مستقبلًا. لا QR أو تكامل حكومي أو شركة توصيل مفترضة.

## الوظائف الفعلية

1. قائمة إصدار مقسمة إلى صفحات، ضمن الخدمات التي يملك الموظف صلاحية إصدارها، مع البحث بمرجع الطلب وشاشة فحص حديثة قبل الإصدار.
2. إعادة استخدام `ApprovalReadiness` و`ServiceEligibility` قبل الإصدار: اعتماد موثق، حساب مواطن نشط، خدمة وقواعد وتقييمات حالية، بيانات ومرفقات ونواقص ومواعيد وفحص وسداد مستوفية بحسب قواعدها. بصمة النموذج ونسخة الطلب والقواعد تمنع الإصدار من شاشة قديمة.
3. سجل وثيقة واحد لكل طلب، مرتبط بصاحبه وخدمته وموظف الإصدار. رقم `INT-[بادئة اختيارية]-[سنة اختيارية]-ULID` يولد على الخادم، مع قيد فريد عالمي في قاعدة البيانات، دون الاعتماد على عدد السجلات. التعارض يتراجع عن العملية برسالة واضحة لإعادة المحاولة؛ لا تغيير لترقيم وثيقة موجودة.
4. تاريخ إصدار مستقل عن `created_at`. حساب الانتهاء فقط من `validity_days` الصريح المعتمد في سياسة الخدمة؛ عند عدم اشتراطه يبقى فارغًا. غياب الإعداد يمنع الإصدار بدل اختراع مدة.
5. سياسة إصدار مجمدة على الوثيقة. الاسم الذي يظهر بالنسخة يحفظ عند الإصدار في `holder_snapshot` مشفر وثابت، حتى لا تغير إعادة إنشاء الملف هوية السجل بعد تعديل الملف الشخصي.
6. نسخة إلكترونية خاصة مع طول وبصمة SHA-256 وقالب ورقم نسخة ضمن سجل `document_copies`. كل إعادة إنشاء تضيف سجلًا وملفًا جديدين؛ لا تمحو النسخة السابقة. التنزيل المحمي يتحقق من الملكية أو صلاحية الخدمة، وإذن تنزيل المواطن، ووجود النسخة وسلامتها في كل مرة.
7. الإصدار وتحديث الطلب وسجل التدقيق وإنشاء النسخة منسقة بمعاملة واحدة. إذا فشل القالب أو التخزين أو التدقيق أو الحفظ، تتراجع السجلات والحالات، ويُحذف فقط الملف الجديد الذي أنشأته المحاولة. تبقى الوثيقة السابقة دون تغيير ويمكن إعادة المحاولة. لا سجلات إصدار نصف مكتملة عند فشل الملف المعتاد.
8. تجديد لطلب تجديد مستقل ومعتمد، يختار الموظف فيه الوثيقة السابقة. يتحقق من صاحبها ونوعها وقواعد حالتها وتواريخها ونافذة التجديد ومن عدم وجود وثيقة لاحقة. عند اشتراط الأصالة، يُفحص المستند المختار نفسه، لا مستند آخر للمواطن. بعد نجاح الإصدار فقط تصبح القديمة `superseded`، مع علاقة وسجل تجديد محفوظين. قيد فريد للوثيقة السابقة يمنع تجديدين متعارضين.
9. اختيار الاستلام من المواطن أو الموظف المخول بالتسليم: مركز من القائمة المعتمدة أو عنوان حين تتيح الخدمة التوصيل. العنوان مشفر ولا يظهر في قوائم الموظفين أو سجلات العمليات. يُطلب مرجع تأكيد الاستلام فقط دون بيانات شخصية إضافية.
10. تسليم داخلي بصلاحية مستقلة: تجهيز، خروج للتوصيل عند طريقة العنوان، تسليم، فشل، إرجاع، وإعادة تجهيز بسبب مسجل. لا تعديل للطريقة أو العنوان بعد بدء الإجراءات. المواطن لا يستطيع تأكيد التسليم أو تعيين حالته.
11. إكمال الطلب حسب السياسة المجمدة: عند الإصدار، أو بعد التسليم الموثق. عند اشتراط النسخة يجب أن تكون سليمة؛ عند اشتراط التسليم لا يكفي إنشاء الوثيقة. يسجل وقت الإكمال ومنفذه. الانتقال المركزي يمنع `processing` أو `completed` دون وثيقة مطابقة وشروط الإكمال، حتى عند استدعائه مباشرة من كود آخر.
12. سجل أحداث غير قابل للتعديل أو الحذف عبر النماذج للإصدار والتجديد وإعادة إنشاء النسخة واختيار الاستلام وتغيرات التسليم والإكمال. UUID ومحتوى الأمر يميزان إعادة الإرسال المطابقة من إعادة استخدام الرمز لإجراء مختلف، مع `workflow_version` لرفض التحديث القديم.

## الحالات والصلاحيات

- الطلب: `approved → processing → completed`. الإصدار لا يكمل الطلب تلقائيًا إن كانت سياسة الخدمة تشترط التسليم.
- الوثيقة: `active` بعد الإصدار، و`superseded` بعد نجاح التجديد. انتهاء الصلاحية يعرض من تاريخ الانتهاء دون حذف السجل أو تغيير حالة التسليم.
- التسليم: `awaiting_choice → ready → preparing → out_for_delivery → delivered` للتوصيل. الاستلام الشخصي يسمح بالتسليم من `ready` أو `preparing`. الفشل والإرجاع وإعادة التجهيز لها انتقالات مقيدة وأسباب مطلوبة.
- `can_issue` و`can_deliver` أضيفتا إلى منح الموظف الحالية حسب الخدمة، بقيمة افتراضية false، دون أدوار جديدة. المدير يضبطهما من `/admin/review-permissions`، ولا يمنح الاعتماد وحده إصدارًا أو تسليمًا. المدير نفسه ليس مُصدرًا تلقائيًا.
- مسارات المواطن تستخدم علاقة وثائقه فترد 404 لوثيقة الغير، والموظف يحتاج منح الخدمة. الملفات ليست في `public` ولا تستعمل `storage:link` أو روابط عامة.

## إعداد الخدمة قبل الاستخدام

من إعداد الخدمة `/admin/services/{id}/edit`، أدخل سياسة `issuance_rules` وفق مرجع موثوق. تركها فارغة يمنع الإصدار. مفاتيحها:

| المفتاح | المعنى |
| --- | --- |
| `enabled` | تمكين الإصدار بعد استكمال الإعداد |
| `source_reference` | مرجع اعتماد إعداد الإصدار |
| `expiry.required` | هل يشترط تاريخ انتهاء |
| `expiry.validity_days` | مدة موثقة بالأيام عند اشتراط الانتهاء؛ لا قيمة قانونية افتراضية |
| `number_prefix` | بادئة داخلية اختيارية لاتينية؛ لا تلغي INT |
| `include_year` | إدراج السنة في المرجع الداخلي |
| `electronic_copy` | `internal_html` أو `none` إذا لم تكن النسخة مطلوبة |
| `citizen_download` | السماح بتنزيل النسخة للمواطن |
| `delivery.methods` | `pickup` و/أو `address` حسب الإتاحة الفعلية |
| `delivery.centers` | أسماء مراكز حقيقية معتمدة عند الاستلام الشخصي |
| `completion_stage` | `issuance` أو `delivery` |

تغيير سياسة الإصدار يزيد `rules_version`؛ ينبغي تحديث التقييمات والأدلة المرتبطة وفق إجراءات المشروع قبل الإصدار. السياسة تجمد للوثيقة الصادرة؛ التعديلات التالية لا تغير تواريخها وطريقة إكمالها التاريخية. لا رسوم إعفاء أو قواعد استبدال مخترعة؛ يستمر السداد وفق المتطلب السابع. الاستبدال/بدل فاقد وإعادة إصدار سجل جديد بعد خطأ تحتاج سياسة مستقلة، وتُرفض صراحةً في خدمة الإصدار الحالية. إعادة إنشاء **النسخة الإلكترونية** مدعومة ولا تنشئ رقم وثيقة جديدًا.

التواريخ تستخدم منطقة Laravel المضبوطة في المشروع (`config('app.timezone')`) لا تاريخ المتصفح. لا تغير ضمن المهمة إعداد المنطقة الزمنية للمشروع.

## التخزين والتعامل مع الفشل

القرص `documents` محلي خاص في `storage/app/issued-documents`، مع ملفات UUID داخل `copies/`. لا أسماء أشخاص أو أرقام وطنية في المسار. استجابة التنزيل attachment وبها `no-store`, `nosniff` وسياسة CSP مقيدة؛ الملف HTML محفوظ محليًا بلا سكربتات أو روابط تحقق. لا يعرض الملف التالف؛ يعاد 409 ورسالة آمنة، ويمكن للموظف إعادة إنشائه مع سبب مسجل. يجب الاحتفاظ بمفتاح تشفير Laravel لاسترجاع العناوين واسم حامل السجل، وحماية النسخ الاحتياطية ومساحة التخزين.

إنهاء عملية PHP قسرًا بين كتابة الملف وتثبيت المعاملة قد يترك ملفًا غير مرتبط، لأن التخزين ونظام القاعدة ليسا معاملة موزعة؛ لا ينتج عنه سجل وثيقة مثبت دون ملف صحيح في مسار الإصدار الطبيعي. لا توجد أداة تنظيف تحذف ملفات آليًا ضمن هذه المهمة؛ النسخ التاريخية تحتفظ بها المنصة.

## المراجعة والحدود

أثبت اختبارا انحدار فشلهما قبل إصلاح فحص أصالة الوثيقة المختارة وثبات اسم النسخة المعاد توليدها. أكدت إعادة المراجعة المستقلة الإصلاحين وفحوص دورة الحالات والتدقيق والتنزيل دون عائق ملموس متبقٍ في نطاق المراجعة. الواجهات اختُبرت عبر HTTP وتجميع Blade؛ لم تُجر معاينة بصرية بالمتصفح.

لا إصدار قانوني أو PDF رسمي أو ختم أو توقيع حكومي، ولا تحقق خارجي أو تسليم لشركة متكاملة. لم تنفذ الإلغاء أو بدل فاقد أو إعادة إصدار وثيقة جديدة؛ تتطلب سياسات مستقلة معتمدة. لم تنفذ متطلبات الإشعارات والتقارير والمساعد الذكي اللاحقة.
