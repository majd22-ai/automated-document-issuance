# مراجعة واعتماد الطلبات — المتطلب الوظيفي الثامن

## الفحص والنطاق

المشروع Laravel 12.65.0 وPHP 8.2.12، جلسات Laravel وMySQL محلي (MariaDB 10.4.32). أُعيد استخدام جداول المستخدمين والخدمات والطلبات والوثائق والمرفقات الخاصة والتقييمات والمواعيد والفحوص والرسوم والسداد من المتطلبات السابقة. كانت قائمة الموظف للقراءة فقط، ولم توجد قرارات مراجعة أو نواقص أو صلاحيات مراجعة حسب الخدمة. لم تُضف مكتبات أو أدوار جديدة أو بيانات تشغيل تجريبية.

## ما أصبح يعمل

- قائمة موظف مقسمة إلى صفحات من 15 طلبًا؛ البحث بالمرجع والتصفية بالخدمة والحالة وتاريخ التقديم والمسؤول والطلبات المسندة إليّ ونتيجة الفحص المحفوظة. نتيجة القائمة مؤرخة بطبيعتها وليست ضمانًا لاستمرار الاستيفاء؛ شاشة القرار والقرار نفسه يعيدان الفحص.
- صلاحيات مستقلة لكل موظف وخدمة: المراجعة والاعتماد والإسناد، يمنحها المدير صراحةً في `/admin/review-permissions`. لا منح تلقائيًا للموظفين أو المدير. صلاحيات الاطلاع والعمليات السابقة بقيت كما كانت؛ شاشة المراجعة وملاحظاتها الداخلية تتطلب المنح الجديدة.
- استلام غير المسند، والإسناد أو تغيير المسؤول مع تسجيل السبب والمنفذ والتاريخ. المستلم يجب أن يكون موظفًا نشطًا مخولًا بمراجعة الخدمة. لا تتاح قرارات المراجعة إلا للمسؤول؛ الاعتماد النهائي له صلاحية منفصلة.
- شاشة عربية متكاملة للبيانات والوثائق والروابط المحمية للمرفقات ونتائج التحقق والمواعيد والفحص والسداد وتاريخ القرارات.
- قبول بعد المراجعة، وإرجاع مع سبب ونواقص متعددة، ورفض نهائي مسبب، واعتماد مستقل تمهيدًا للإصدار. جميع القرارات وسجلها تحفظ في معاملة واحدة، والفشل في حفظ السجل يتراجع عن تغيير الحالة.
- المواطن يرى الحالة والأسباب العامة والنواقص والخطوة التالية، دون الملاحظات الداخلية. يصحح حقول النموذج التي حددها الموظف فقط، وفق مخطط النموذج التاريخي، مع حفظ البيانات الأصلية. استبدال المرفقات وتحديث الاتصال والمواعيد يتم عبر مساراتها المحمية الحالية.
- إعادة التقديم تعيد الطلب إلى `submitted`، وتبقى النواقص `awaiting_review` حتى يثبت الموظف استكمالها. لا يستطيع المواطن إغلاق النواقص بنفسه. عند القبول والاعتماد لا يجوز وجود نقص غير محسوم.
- منع تكرار الأوامر باستخدام UUID ومحتوى القرار، ورفض استعمال الرمز لقرار مختلف، ورفض النماذج القديمة عند تغير نسخة الطلب أو القواعد أو الأدلة. البصمة تشمل الوثائق والتقييمات والمرفقات والمواعيد والفحص والسداد والبيانات والنواقص.
- القراءة والرسم وبصمة النموذج في شاشة المراجعة والاستكمال تتم داخل معاملة الأقفال نفسها، حتى لا يُعرض محتوى قديم مع بصمة محتوى أحدث. القرارات تستخدم ترتيب قفل المواطن ثم الخدمة ثم الطلب، مع إعادة التحقق من الصلاحيات.

## الحالات وشروط الاعتماد

`submitted → under_review → accepted → approved`

ومن `under_review` إلى `requires_correction` أو `rejected`؛ ومن الاستكمال إلى `submitted` فقط عبر إعادة التقديم المحمية. لا يوجد مسار لإعادة فتح الطلب المرفوض نفسه. سياسة تقديم طلب جديد مستقلة وتبقى سياسة المشروع السابقة.

الاعتماد يتطلب قبولًا مسجلًا، واستيفاء الشروط الإلزامية الحالية، وعدم وجود نواقص مفتوحة، واستيفاء الموعد والفحص والسداد عندما تتطلب الخدمة ذلك. يشمل ذلك الشروط التي كانت مؤجلة إلى `processing` في المتطلب السابع؛ لا تمر إلى الاعتماد النهائي دون استيفائها. الرسوم المجهولة لا تُعامل كرسوم صفرية، والسداد اليدوي المسجل ليس تأكيدًا من بوابة دفع.

خيار `require_separate_approver` في إعداد الخدمة يفرض اختلاف المعتمد عن صاحب قرار القبول. يطبق إذا كان مفعّلًا في نسخة الطلب التاريخية أو سياسة الخدمة الحالية، حتى لا تتجاوز الطلبات القديمة سياسة فصل فُعلت لاحقًا.

نقطة التكامل المستقبلية `ApprovalReadiness::check($application)` تتحقق من الحالة المعتمدة ووجود قرار الاعتماد والنواقص والشروط الحالية، دون إنشاء وثيقة أو تغيير حالة الطلب. يجب أن يستخدم المتطلب التاسع فحصًا داخل معاملة الإصدار نفسها؛ نتيجة الفحص المستقل قد تتقادم بعد انتهاء معاملته. لا صلاحية تشغيلية للانتقال إلى `processing` أو `completed` ضمن هذا المتطلب، ولا أرقام وثائق أو تسليم أو نظام إشعارات خارجي.

## الملفات الجديدة

- `database/migrations/2026_10_28_000001_add_application_review.php`: أعمدة الإسناد ونسخة المراجعة وبيانات الأصل؛ جداول `service_review_permissions`, `review_decisions`, `request_deficiencies`؛ خيار فصل المعتمد. ترحيل إضافي يحافظ على البيانات، و`down` يحتفظ بتاريخ التدقيق.

- Controllers: `ApplicationReviewController`, `ReviewPermissionController`.
- Form Requests: `ReviewDecisionRequest`, `AssignReviewRequest`, `ResolveReviewDeficiencyRequest`, `ResubmitReviewedRequest`.
- Views: `admin/review-permissions.blade.php`, `citizen/applications/correction.blade.php`, `components/review-history.blade.php`, `employee/applications/readonly.blade.php`.
- Tests: `tests/Feature/ApplicationReviewTest.php`, `tests/Integration/ApplicationReviewConcurrencyTest.php`, `tests/Support/application-review-worker.php`.

التغييرات الأخرى السابقة الموجودة في مساحة العمل لم تُحذف أو تُستبدل.

## التشغيل والتحقق

```powershell
php artisan migrate --force
php vendor/bin/phpunit --do-not-cache-result
php vendor/bin/phpunit tests/Feature/ApplicationReviewTest.php --do-not-cache-result
php artisan view:cache
node --test tests/frontend/portal-demo.test.cjs
```

لاختبار MySQL اضبط الاتصال بقاعدة اختبار ينتهي اسمها بـ `_testing`، ثم شغل المجموعة الكاملة واختبارات التزامن التالية بالتتابع. لا تشغل مجموعتي SQLite وMySQL معًا، لأن اختبارات المرفقات السابقة تستخدم مجلد `Storage::fake` مشتركًا.

```powershell
php vendor/bin/phpunit tests/Integration/ApplicationReviewConcurrencyTest.php tests/Integration/RequestOperationsConcurrencyTest.php tests/Integration/ServiceRequestConcurrencyTest.php --do-not-cache-result
```

اختبارات التزامن تشغل عمليات PHP منفصلة، وتزيل فقط سجلات الاختبار التي أنشأتها في القاعدة المعزولة. لا يستخدم التنفيذ `migrate:fresh`.

## حدود التكامل

يلزم أن يحدد المدير موظفين حقيقيين وصلاحياتهم للخدمات، وأن تُسجل قواعد الخدمة والتقييمات والمواعيد والنتائج والإيصالات المعتمدة. لا تُنشأ تقييمات أو صلاحيات أو سداد وهمي في قاعدة التشغيل. الربط بجهة حكومية أو طبية أو بوابة دفع، والإصدار والإشعارات الخارجية، تحتاج تكاملًا منفصلًا. الواجهات اختُبرت بطلبات HTTP وتجميع Blade؛ لم تُجر معاينة بصرية بالمتصفح.

المراجعة المستقلة اكتشفت احتمال عدم اتساق البيانات المعروضة والبصمة عند التزامن؛ عولج بالأقفال والرسم داخل المعاملة، وأكدت إعادة المراجعة عدم وجود عائق ملموس متبقٍ في نطاقها. أضيف اختبار انحدار للشاشتين، وفحص تغيّر وثائق المواطن وسياسة فصل المعتمد.

## النتائج الفعلية

- المجموعة الكاملة على SQLite: **136 اختبارًا، 996 تأكيدًا ناجحًا**.
- المجموعة الكاملة على MySQL الاختبارية: **136 اختبارًا، 996 تأكيدًا ناجحًا**.
- مجموعة المتطلب الثامن المستهدفة: **20 اختبارًا، 148 تأكيدًا ناجحًا**.
- اختبارات التزامن الفعلية على MySQL: **6 اختبارات، 36 تأكيدًا ناجحًا**؛ منافسة موظفين على الاستلام تنتج مستلمًا واحدًا، ومنافسة معتمدين تنتج قرار اعتماد واحدًا. تشمل أيضًا منع تكرار تقديم الطلب وحجز آخر مقعد وإعادة استخدام الإيصال.
- اختبارات JavaScript القائمة: **5 ناجحة**. تجميع Blade وقائمة المسارات ناجحان. اكتملت معالجة تنسيق Pint؛ لا أخطاء مسافات من `git diff --check`، مع تنبيهات تحويل نهايات الأسطر في ملفات سابقة.
- طُبق الترحيل على قاعدة المشروع: بقي **مستخدم واحد و7 خدمات وصفر طلبات** قبل الترحيل وبعده. جداول الصلاحيات والقرارات والنواقص والمواعيد والفحوص والالتزامات والمدفوعات خالية؛ لا منح أو سجلات تجريبية ضمن قاعدة التشغيل.
- ظهر خطأ في تجهيز اختبار التزامن الجديد بسبب عدم إعادة تحميل القيمة الافتراضية `rules_version` بعد إنشاء خدمة الاختبار؛ صُحح الـ fixture ثم نجحت الاختبارات الستة. لم تُخفف قيود قاعدة البيانات.
