# الجزء الثالث: البصمة التجريبية والمراجعة والنموذج النهائي

## التنفيذ

أعيد استخدام طلب البطاقة والصورة الخاصة والشاهدين والمصادقات والصلاحيات والإشعارات الموجودة. أضيف استقبال بالمرجع الداخلي، تسجيل الحضور وفحص الوثائق، محاكاة بصمة محفوظة على الخادم، ومراجعة إدارية. الإجراءات الإدارية: اعتماد تجريبي، إعادة للموظف، تصحيح، أو رفض بسبب. التصحيح يحتفظ بالطلب الأصلي ورقمه وسجله، ويفتح مراجعة جديدة تحتاج مصادقة ونتيجة بصمة جديدتين.

تعرض متابعة المواطن حالته وأسباب التصحيح أو الرفض المخصصة له؛ لا تعرض الملاحظات الداخلية. الصور تبقى خاصة. لا يستطيع المواطن اعتماد طلبه، وتخضع صلاحيات الموظف للخدمة المسندة إليه. تمنع المعاملات والأقفال والإصدارات ومفاتيح العمليات تكرار النجاح والقرارات المتعارضة.

## قاعدة البيانات

Migration: `database/migrations/2026_10_29_000003_complete_identity_trial_workflow.php`، طُبقت محليًا بنجاح دون حذف بيانات.

- `identity_card_forms`: إصدار المراجعة، وقت الحضور والموظف ومرجع فحص الهوية، وقت فحص الوثائق، حالة البصمة، وبيانات فتح التصحيح وإعادة الإرسال.
- `identity_card_attestations`: إصدار النموذج، اسم المواطن وقت المصادقة، وموظف ووقت تسجيل إجراء الأمن الورقي. تصبح المصادقة مرتبطة بإصدار النموذج مع الاحتفاظ بالتاريخ.
- `identity_fingerprint_operations`: مرجع ومفتاح فريدان، الطلب والإصدار، مصدر النتيجة والنتيجة والموظف والوقت والخطأ ومرجع الإثبات. بصمة سياق البيانات `input_fingerprint` مجرد تجزئة لسلامة السياق وليست قالب بصمة حيوية.
- `identity_administrative_decisions`: الطلب والإصدار والعملية والقرار ومفتاحه الفريد والموظف والوقت والملاحظة الداخلية والسبب المخصص للمواطن.

تنقل الترقية طلبات الجزء الثاني المؤهلة التي لم تسجل نتيجة بصمة ناجحة إلى انتظار الحضور، دون إعادة فتح الطلبات المنتهية.

## التشغيل والتجربة

من مجلد المشروع، شغّل MySQL ثم:

```powershell
php artisan migrate
php artisan serve --host=127.0.0.1 --port=8000
```

تعمل المحاكاة في `APP_ENV=local` فقط، مع `IDENTITY_ATTESTATION_SIMULATION=true` و`IDENTITY_FINGERPRINT_SIMULATION=true`. يبقى `IDENTITY_MANUAL_FINGERPRINT_RESULT=false` افتراضيًا.

1. يدخل المواطن إلى `/citizen/identity-card`، يكمل البيانات والصورة والشاهدين ويرسل الطلب.
2. يراجع الموظف الصورة عبر المراجعة الموجودة؛ يستكمل مسار المصادقة المختار. محاكاة الجوال لجهة العمل وعاقل الحارة متاحة للمخولين فقط؛ الشاهدان لهما تسجيل حضور ومراجعة مستقلة. عند لزوم إجراء الأمن، يُسجل مرجعه الورقي منفصلًا.
3. الموظف المخول بــ`can_review` يدخل `/identity-workflow/reception` ويبحث بالمرجع، يفحص الوثائق ويسجل الحضور ومرجع الفحص.
4. يفتح شاشة الجهاز، ويمكنه اختبار الفشل ثم إعادة المحاولة. كل محاولة مسجلة، ونجاح المحاكاة ينقل الطلب إلى المراجعة الإدارية.
5. المدير أو الموظف المخول بــ`can_approve` يدخل `/identity-workflow/administration` ويتخذ القرار المناسب. طلب التصحيح يفتح المراحل للمواطن مع الاحتفاظ بالتاريخ.
6. بعد اكتمال الشروط والاعتماد التجريبي تظهر الطباعة من تفاصيل الطلب. يعرض النموذج البيانات الفعلية والصورة والشهود والإقرار وأماكن التوقيع والمصادقة وإجراء الأمن وموظفي المعالجة ومصدر نتيجة البصمة.


## حدود التنفيذ والتكامل

المصادقة والبصمة محاكاتان محليتان واضحتان؛ لا تُخزن صور أصابع أو قوالب حيوية، ولا تصدر بطاقة حكومية أو رقمها الرسمي. نتائج المحاكاة وسجلات القرارات غير قابلة للتعديل عبر النماذج، ولا تتحول نتيجة المحاكاة إلى نتيجة حقيقية.

التسجيل الإداري لنتيجة جهاز حقيقي مسار منفصل معطل افتراضيًا، ويتطلب موظفًا مخولًا ومرجعًا ووقت تنفيذ وإقرارًا صريحًا، ويعرض أنه إدخال يدوي. التكامل الآلي الحقيقي يحتاج SDK أو API موثقًا وموافقة الجهة المختصة؛ لم يُخترع اتصال بالجهاز.

توجد معاينة عربية RTL وتنسيق طباعة A4 وزر للطباعة وزر «حفظ PDF من نافذة الطباعة» باستخدام المتصفح. لم تضف مكتبة PDF خادمية، ولم تُنفذ تجربة طباعة أو تصدير PDF مرئية داخل متصفح؛ اختُبر توليد الواجهة وربط أزرار الطباعة فقط. يلزم التحقق البصري من الصفحات والهوامش في المتصفح المستخدم قبل اعتماد إخراج نهائي.
